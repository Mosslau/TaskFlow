## 1. 评估方法

### 1.1 模块划分

能力清单按 **14 个模块、3 个领域**组织,共 140 个功能点:

| 领域 | 模块 |
|---|---|
| **A. 组织与权限** | ① 身份与组织 ② 权限与安全 ③ 合规与认证 |
| **B. 业务与协作** | ④ 任务与工作流 ⑤ 协作与内容 ⑥ 计划与日程 ⑦ 通知与集成 ⑧ 报表与度量 ⑨ 搜索与知识 ⑩ 用户体验 |
| **C. 平台与生态** | ⑪ AI 与智能化 ⑫ 平台与运维(SRE·供应链) ⑬ 开放与生态 ⑭ 产品化与运营 |

> 各模块标题后的百分比为**复核修正后**的得分,括号内为原值;未标注者表示复核后未变。

### 1.2 评分口径

- 单模块得分 = (✅×1 + 🟡×0.5) ÷ 该模块功能点数 × 100%(⚠️ 视为"判定成立但附前提",计分同 ✅)
- **综合企业就绪度(主口径·模块等权)** = 14 个模块得分算术平均 = **21%**
- **综合企业就绪度(次口径·条目加权)** = (✅×1 + 🟡×0.5) ÷ 140 = **16%**(原 18%)
  - 两口径差异来源:主口径**每个模块权重相同,与模块内条目数无关**。⑪ AI 有 34 项(占全部功能点 **24%**)却只占 1/14 权重,与只有 5 项的 ⑬ 等价;次口径按条目数加权,故更低。**对外引用建议同时给出两个数**,避免只挑较高的那个。
- **门槛项**:企业采购/IT 安全评审必问,缺失会导致无法入库(第 4 节 P0)
- **加分项**:影响采纳率与效率,不构成准入障碍(P1)
- **规模化项**:客户与数据量增长后才需要(P2)

### 1.2.1 两个必须说明的口径问题(复核新增)

1. **P2 模块不应参与主分**:⑪ AI 的 34 项全部计 0 分,占全部功能点 24%,是拉低综合分最大的单一因素——而它在 §4 中又被列为 **P2("客户与数据量增长后才需要")**。**"不着急"与"决定总分"不能同时成立**。建议对外只引用**剔除 ⑪ 后的主分**,或为 ⑪ 单列"智能化就绪度"副指标。
2. **§6 的规模/NFR 基线是未确认的假设值**,却已被用于判定"不达标":最典型是 §4 P0-6 依据自设的 `RPO ≤15 分钟` 把备份判为不达标,而 **PRD 第 553 行原文为 `RPO ≤24h / RTO ≤4h`**,`deploy/scripts/backup.sh` 亦对齐 24h。**同一项目存在两个互相冲突的 RPO 目标**。凡据此判定的项,应同时给出 PRD 口径(见 §6.3 修正说明)。

### 1.3 口径说明

早期版本仅统计"功能地基"且口径偏松,给出过 40% 的综合分。本版把 AI、合规认证、SRE 与供应链、用户体验、产品化运营、度量与自动化并入评估,并统一 ✅=1 / 🟡=0.5 的算法,因此数值不可直接比较——本版结论更能代表**企业就绪度**。

> ⚠️ **版本溯源(2026-09-10 复核补充)**:上文"早期版本(40%)"即 `main @ 4c5cb20` 提交中的本文件。原文档头曾把基线误标为该提交,造成"用被自己否定的版本作为基线"的矛盾,**现已更正为 `5a7713e`**。
> 另:`4c5cb20` 之前的版本口径为"10 模块 / 112 功能点",经 3 次提交扩至"14 模块 / 140 功能点"——**引用历史分数时须同时注明模块数与条目数,否则不可比**。

## 5. 演进路线

> **估时说明(复核修正,2026-09-10)**:原三批次估时**严重不足**(约实际工作量的 1/3–1/4)。本章已按交付物重新拆分并给出区间,新增**批次零(缺陷修复)**。所有估时假设:**单人全职、含回归测试、不含企业侧配合(IdP/对象存储/中间件采购)等待时间**。

### 批次零:缺陷修复(§4.1,约 1-2 周 / 单人)

> **前置于批次一**。7 条均为已定位的确定性缺陷,修复成本低、收益直接;尤其缺陷 1 不修则**全新部署无法完成**,后续任何交付都无法验证。

| 缺陷 | 修复要点 | 验收 |
|---|---|---|
| 1 部署阻断 | `deploy/postgres/init/` 增 `CREATE EXTENSION pg_trgm`(或迁移前置脚本),并写入 `deploy/README` | 全新 docker 初始化能跑完 V1 迁移 |
| 2 权限缓存 | 只读接口补 `@RequirePerm`,或 `currentPerms()` 加回源 | 矩阵新增/收回权限均在**下一次请求**生效,不返空列表 |
| 3 强制改密 | 网关或 auth 拦截器:未改密只放行改密/登出接口 | 用初始密码调业务接口被拒 |
| 4 审计完整性 | `deploy/` 落 `REVOKE UPDATE,DELETE ON audit_log`;应用去掉 update/delete 出口;审计写入端点补权限或改内部接口 | 直连库无法改审计;外部无法注入审计记录 |
| 5 统计越权 | stats 复用可见性语义,或明确以 `viewStats` 为全域授权并写入 PRD 例外 | 越权用例:普通用户看不到全域统计 |
| 6 通知可靠性 | `processed_event` 改为"分发成功后再登记";DLQ 加回放开关 + 告警 | 消费失败后通知最终可达,且失败可观测 |
| 7 删除审计 | 删除改软删,或先归档 timeline;审计与业务同事务 | 被删任务的历史动作仍可追溯 |

**风险与依赖**:缺陷 2/5 涉及权限语义,需回归全部可见性用例;缺陷 6 改动事件消费幂等语义,需重跑 M3 通知验收用例。

### 批次一:企业化地基(P0)

> **复核修正估时**:原"约 6 周 / 单人"严重不足。8 项交付中含**可配置工作流引擎 + 全量审计 + 四中间件集群 + PITR + 表分区 + SLO**,实际约 **4-6 个月 / 单人**。建议拆为两段:
>
> - **1a 运维硬化与可迁移性(3-4 周)**:附件对象存储、服务 ≥2 副本 + LB、PG/Redis/MQ/Nacos 集群、PITR 与恢复演练、监控告警与 SLO、表分区。**收益最高、依赖最少、基本不触碰业务语义,建议先做。**
> - **1b 组织与流程可配置化(6-10 周)**:SSO、数据范围 + 字段级权限、可配置工作流 + 自定义字段、全量审计 + 哈希篡改检出。**改造面最大,须回归全部状态机与可见性用例。**
> - SSO 可与 1b **并行**,但依赖企业 IdP 配合,不属纯开发工时。

| 交付 | 技术落点 | 验收要点 |
|---|---|---|
| SSO 接入 | 网关引入 `spring-boot-starter-oauth2-resource-server`(RS256 + JWKS);auth 对接企业 IdP(OIDC);本地账号保留兜底 | 扫码登录成功;官方 `JwtDecoder` 完成校验;本地账号仍可用 |
| 数据范围 + 字段级权限 | `role_permission` 增 `data_scope`;部门表升级为树(parent_id);`TaskService.applyVisibility` 改为读配置;响应按角色裁剪字段 | 同角色不同范围产生不同可见集;越范围 2001;敏感字段按角色隐藏 |
| 可配置工作流 + 自定义字段 | 新增 `workflow_def` / `workflow_transition`;任务表加 `ext JSONB` + `field_def` | 两部门不同流程并存;非法流转仍 2002;动态字段在列表/详情/导入导出全通 |
| 全量审计 + 防篡改 | Service 层统一记录 `audit_log`(动作/实体/前后值 diff);哈希链校验 | 抽查 5 类动作均有 diff;篡改可被检出 |
| 无状态化 + 高可用 | 附件迁 MinIO/S3 + 预签名 URL;服务 ≥2 副本 + LB;PG 主从或托管、Redis 主从、RabbitMQ 镜像或托管、Nacos 3 节点 | 杀实例不中断;附件可被任一副本读取 |
| 备份与灾备 | WAL 归档 + PITR;备份加密 + 异地副本;恢复演练脚本化 | 达成 RPO ≤15min、RTO ≤2h 并留演练记录 |
| 数据规模治理 | `task` 按 created_at 分区(或复合索引 + BRIN);`task_timeline` 分区/归档;审计冷热分层 | 50 万任务下 P95 仍 ≤1s |
| 监控告警与 SLO | Prometheus + Grafana;SLI/SLO 定义与告警规则;值班与事故流程 | 看板可用;告警可触达;流程演练一次 |

**风险与依赖**:SSO 依赖企业 IdP 配合;工作流引擎改造面最大,需回归全部状态机用例;数据范围影响所有查询,必须由统一入口收口;对象存储迁移需处理存量附件。

### 批次二:效率与集成(P1)

> **复核修正估时**:原"约 4 周"不足,实际约 **3-4 个月 / 单人**。其中"看板 + 拖拽 + watchers/@提及 + 保存视图 + 个性化首页 + 移动端 PWA"单项即 3-4 周;OpenSearch 集群与事件驱动索引一致性另需 2-3 周。
> **建议排序**:先做**全文检索**与**体验层**(用户体感最直接、无外部依赖),IM/Webhook 与工时/项目集按客户实际诉求排期。

| 交付 | 技术落点 | 验收 |
|---|---|---|
| 全文检索 | OpenSearch + 事件驱动索引(outbox 增加 search 消费者) | 高亮与相关度可用;延迟 <5s |
| IM 通知 + Webhook | notification 增加通道(企微机器人);对外订阅表 + 签名 + 重试 | 建任务后 IM 收到卡片;外部系统收到签名事件 |
| 工时与成本 | `worklog` 表 + 审批;按人/项目汇总 | 登记审批闭环;成本报表可导出 |
| 项目集与甘特 | `project` / `portfolio` + 任务依赖;甘特视图 | 依赖冲突校验;拖拽改期 |
| 批量与模板 | 列表多选批量操作;任务/项目模板 | 批量 100 条 <2s;模板一键生成任务树 |
| 自定义报表与周报 | 报表定义(维度/指标)+ 定时邮件 | 订阅周报自动发送 |
| 体验层 | 看板视图 + 拖拽、watchers/@提及、保存视图与个性化首页、移动端 PWA | 关键场景移动端可用 |
| 度量字典 | 指标口径字典 + 数据质量监控 + 工程度量 | 口径可查;与手工核算一致 |

### 批次三:规模化与产品化(P2)

> **复核修正估时**:原"约 4 周+"不足,实际 **6 个月以上 / 单人**。**仅多租户一项**(5 个服务 + 全部表 `tenant_id` + 拦截器 + JWT + Redis 键前缀 + MQ 载荷 + 矩阵 + 前端租户切换)即 **6-10 周**;AI 能力文档自估 A 阶段(只读 MCP + Coordinator + 2 Skill + HITL + 审计配额)另需 2-3 周。
