# TaskFlow 企业级能力对照与演进路线

> 评估日期:2026-09-10 | 基线:`main @ a8d7a8d`
> 图例:✅ 已具备 · 🟡 部分/简化 · ❌ 缺失
> 目的:以"企业级任务管理系统"的通行能力清单为标尺,盘点 TaskFlow 现状、量化差距、给出分批演进路线与估时。

---

## 1. 评估方法

- **能力清单**:按企业软件的 10 大模块拆解(组织/权限/任务/协作/计划/通知/洞察/搜索/平台/开放),每模块列出通行功能点。
- **状态判定**:✅ 已交付并有验收证据 · 🟡 有实现但简化或依赖外部条件 · ❌ 未实现。
- **模块得分** = 该模块功能点加权(✅=1、🟡=0.5、❌=0)后折算百分比;**综合得分**为 10 模块算术平均。
- **门槛判定**:能被企业采购/IT 部门接受所必需的能力,列为 P0。

## 3. 成熟度总览

| 模块 | 得分 | 一句话 |
|---|---|---|
| 权限与安全 | 63% | 项目最强项:矩阵、限流、越权防护、令牌治理都很扎实 |

| 计划与日程 | 42% | 月历可用,缺甘特/项目集 |
| 任务与工作流 | 40% | 单流程做得很细,但**不可配置** |
| 搜索与知识 | 40% | 够小数据量用,缺全文检索 |
| 开放与生态 | 38% | 只有单向最小 API |
| 协作与内容 | 36% | 评论附件有,知识/审批无 |
| 报表与洞察 | 36% | 预置看板好,缺自定义与组织维度 |
| 通知与集成 | 33% | 站内+邮件扎实,无 IM/Webhook |
| 平台与运维 | 29% | 短板:HA、CI/CD、监控告警、备份演练 |
| **综合** | **40%** | 单组织内部使用的"功能性系统";企业采购清单还差 5 个资格项 |

> 解读:**功能闭环程度高(可作为单组织生产使用),企业化程度偏低(组织模型、集成、运维治理)**。这不是设计能力问题,而是产品定位问题——当前 PRD 明确是"企业内部单机部署 + 单组织"。

## 5. 演进路线(三批)

### 批次一:企业化地基(P0,约 4 周 / 单人)

| 交付 | 技术落点(结合现有架构) | 验收要点 |
|---|---|---|
| SSO 接入 | 网关引入 `spring-boot-starter-oauth2-resource-server`(RS256 + JWKS);auth 侧对接企业 IdP(OIDC);保留本地账号作为兜底 | 企业微信/钉钉扫码登录成功;JWT 校验由官方 `JwtDecoder` 完成;本地账号仍可用 |
| 数据范围权限 | `role_permission` 增 `data_scope` 维度(本人/本部门/部门树/指定/全部);`TaskService.applyVisibility` 改为读范围配置;部门表升级为树(parent_id) | 同一角色配置不同范围,可见任务集合随配置变化;越范围访问 2001 |
| 可配置工作流 | 新增 `workflow_def`(状态集)、`workflow_transition`(流转 + 角色 + 条件);状态机执行器替换硬编码分支;timeline 记录按配置渲染 | 两个部门用不同流程并存;非法流转仍 2002;验收沿用 16 条里的状态机用例 |
| 自定义字段 | 任务表加 `ext JSONB`;`field_def`(类型/校验/可见角色);列表与详情动态渲染 | 新增"客户名称/预算"字段;导入导出兼容;字段级权限生效 |
| 全量审计 | 统一在 Service 层用 AOP/事件记录 `audit_log`(动作、实体、前后值 diff) | 抽查 5 类动作(创建/编辑/转派/删除/权限变更)均有审计且含 diff |
| 运维硬化 | K8s/Compose 多副本 + 附件迁对象存储 + Prometheus/Grafana + 告警规则 + 备份恢复演练 | 杀一个服务实例不中断;恢复演练 RTO<2h;看板与告警可用 |

**风险与依赖**:SSO 依赖企业 IdP 侧配合;工作流引擎是最大改造(需回归全部状态机用例);数据范围会影响所有列表/详情查询(建议用统一 `applyVisibility` 收口)。

### 批次二:效率与集成(P1,约 4 周)

| 交付 | 技术落点 | 验收 |
|---|---|---|
| 全文检索 | OpenSearch/ES + 事件驱动索引(outbox 增加 search 消费者);标题/描述/评论/附件名 | 检索带高亮与相关度;与库内数据延迟 <5s |
| IM 通知 + Webhook | notification-service 增加 Webhook/IM 通道(企业微信机器人);对外事件订阅表 + 签名校验 + 重试 | 建任务后企业微信收到卡片;外部系统能收到签名 webhook |
| 工时与成本 | `worklog` 表(人/任务/日期/小时/备注)+ 审批;报表按人/项目汇总 | 工时登记与审批闭环;成本报表可导出 |
| 项目集与甘特 | `project`/`portfolio` 表 + 任务依赖(前置关系)+ 甘特视图 | 依赖冲突校验;甘特拖拽改期 |
| 批量操作与模板 | 列表多选 + 批量指派/改期/归档;任务/项目模板 | 批量 100 条 <2s;模板一键建任务树 |
| 自定义报表与周报 | 报表定义(维度/指标/图表)+ 定时邮件(复用邮件通道) | 保存并订阅周报,按周自动发送 |

## 6. 明确**不做**(避免过度设计)

| 项 | 理由 |
|---|---|
| 自研 IM / 视频会议 | 用企业现有 IM,只做集成 |
| 自研文档协同(在线编辑) | 接 Office/腾讯文档,不重造 |
| 复杂 BPMN 全功能引擎 | 只做"状态 + 流转 + 审批节点"的轻量配置,不引入 Activiti/Flowable 全家桶 |
| 多币种财务核算 | 一期只做工时与成本估算,不做财务系统 |
| 自研移动 App | 先做 PWA / 企业微信内嵌 H5 |

## 7. 决策建议

| 场景 | 建议 |
|---|---|
| **单组织内部使用(当前 PRD)** | 维持现状即可;仅补 P0-4(审计全量)与 P0-5(运维硬化)两项低成本高收益项 |
| **要进企业采购清单** | 必须先做 P0-1(SSO)与 P0-2(可配置工作流)——这两项决定"能不能被第二个部门/第二家公司用起来" |
| **要做对外 SaaS** | 在 P0 基础上加 P2-1(多租户):`tenant_id` + MP 租户插件 + 缓存键前缀 + 事件带租户,是成本最低的 SaaS 化路径 |
| **客户少但要求物理隔离** | 走"每客户独立部署实例",零代码改造,用运维成本换隔离(最快上线路径) |
