## 1. 初始化 admin 与首登强制改密

### 1.1 初始化

- 数据库由 Flyway 迁移自动初始化（`auth-user-service/src/main/resources/db/migration/`）：
  - `V1__init_auth_user.sql`：建 department / role / app_user / role_permission / audit_log / api_key 六表及约束；
  - `V2__seed_auth_user.sql`：种子「默认部门 + 3 角色 + 42 行默认权限矩阵 + 初始 admin」。
- admin 初始口令：开发种子为 `Admin@123`（生产部署应由部署脚本/运维随机生成后覆盖，见 V2 注释与 deploy/README §6/§9）。种子已置 `must_change_password=TRUE`，**首次登录强制改密**。

### 1.2 首登强制改密流程（正常路径）

1. 浏览器打开前端（开发 http://localhost:5173；裸机 http://<host>:8080），用初始口令登录；
2. 登录响应 `user.mustChangePassword=true` 时前端自动弹出「强制改密」对话框（`frontend/src/views/login/components/ForceChangePasswordDialog.vue`），仅允许继续改密；
3. 输入旧口令 + 新口令（规则：8~64 位且同时含字母与数字，接口 PUT /auth/api/v1/password）；
4. 改密成功：`must_change_password=false`，**该用户此前所有 JWT 拉黑、刷新令牌失效**，需重新登录。

> 说明（实测口径）：强制改密标记由前端流程强约束；后端对已登录令牌不因标记拦截业务接口（实测 admin 在 TRUE 状态下 API 全通），因此若绕过前端直连 API，请自行确保改密流程完成。

### 1.3 应急重置路径

**路径 A：有可登录的 admin 时（推荐）** —— 重置任意用户口令：

```bash
# 登录拿 admin 令牌后：
curl -X PUT http://127.0.0.1:8000/auth/api/v1/users/{userId}/password-reset \
  -H "Authorization: Bearer $TOKEN"
# 响应 data.newPassword 随机口令仅此一次，must_change_password 置 TRUE，
# 交给本人走 1.2 首登强制改密。
```

**路径 B：admin 自身口令丢失 / 无人可登录（DB 兜底）** —— 把 admin 恢复为出厂口令 `Admin@123` 并强制改密（与 V2 种子同一 BCrypt 哈希）：

```bash
PGPASSWORD=root psql -h 127.0.0.1 -U postgres -d auth_user_db -c \
"UPDATE app_user SET password_hash='\$2y\$10\$yQBFrOqebPqT2IVrlWx2ZuxG2N9ReAO7qo05/.2NRMOS5TMg93Xk.', must_change_password=TRUE WHERE account='admin';"
```

注意点：
- shell 单引号内 `$` 需转义为 `\$`（如上）；若直接粘贴 SQL 到 psql 交互端则不用转义；
- 该哈希即 bcrypt("Admin@123")（cost=10），仅用于恢复出厂，恢复后务必走 1.2 强改密；
- 该 SQL 亦已记录于 [docs/本地中间件.md](本地中间件.md) 与本次验证报告相关章节。

## 2. 权限矩阵默认值复核表（3 角色 × 14 权限点，与库一致）

库内实查（`auth_user_db.role_permission` join `role`，42 行）：与 PRD 3.3 默认矩阵、种子 SQL、`GET /auth/api/v1/permissions/matrix` 输出**逐格一致**。✓=enabled(true)，—=enabled(false)。

| 权限点 | admin（系统管理员） | taskAdmin（任务管理员） | user（普通用户） |
|---|---|---|---|
| viewAll（查看全部任务） | ✓ | — | — |
| create（创建任务） | ✓ | ✓ | — |
| editOwn（编辑自己创建的任务） | ✓ | ✓ | — |
| deleteOwn（删除自己创建的待办任务） | ✓ | ✓ | — |
| transferOwn（转派自己创建的任务） | ✓ | ✓ | — |
| prioOwn（调自己任务的优先级） | ✓ | ✓ | — |
| dueOwn（调自己任务的到期时间） | ✓ | ✓ | — |
| viewAssigned（查看指派给我的任务） | ✓ | ✓ | ✓ |
| updateAssigned（更新指派给我的任务：受理/进度/提交验收） | ✓ | ✓ | ✓ |
| transferAssigned（转派指派给我的任务） | ✓ | ✓ | ✓ |
| viewStats（查看统计） | ✓ | ✓ | — |
| exportData（导出 CSV） | ✓ | ✓ | — |
| manageUser（用户/部门管理） | ✓ | — | — |
| setPerm（权限矩阵维护） | ✓ | — | — |
| **小计** | **14 ✓** | **11 ✓ / 3 —** | **3 ✓ / 11 —** |

复核 SQL：

```sql
SELECT r.role_key, rp.permission_key, rp.enabled
FROM role_permission rp JOIN role r ON r.id = rp.role_id
ORDER BY r.role_key, rp.permission_key;   -- 42 行
```

安全规则（代码强制）：
- `admin` 的 `manageUser`、`setPerm` 不可置 false（返回 3009，防系统失去管理入口）；
- 矩阵改动**即改即存**并写审计日志（action=`permission.matrix.update`），下一次请求即生效；
- 角色仅 3 个预置，一期不支持自定义角色（app_user.role_id 每用户一个）。

## 3. 运维操作手册

### 3.1 启停

**开发环境（源码运行，本仓库）**

```bash
cd TaskFlow
./start.sh              # 仅后端：gateway/auth/task/notification/stats（依赖 brew 中间件自检拉起）
./start.sh --frontend   # 额外启动前端 Vite dev (:5173)
./stop.sh               # 按 .pids/*.pid 停止全部后端（含兜底 pkill spring-boot:run）
```
- 健康检查：网关 `curl http://127.0.0.1:8000/auth/api/v1/ping` 返回 `{"code":0,...}`；start.sh 已内置逐服务就绪等待（45×2s）。
- 单独重启某服务：`mvn spring-boot:run -pl task-service -Dmaven.repo.local=$PWD/.m2/repository`（后台 nohup 请参照 start.sh 写法），或用 stop.sh 后改 .pids 重起。

**部署环境（jar/容器，M6.3 产物，详见 deploy/README.md）**

```bash
# 方式 A：Docker Compose 一键部署
cd deploy && ./build.sh && cp .env.example .env   # 编辑必改项见 §4
docker compose up -d --build                       # 前端 :8080 / 网关容器内 :8000
docker compose ps; docker compose logs -f --tail=100 gateway-service

# 方式 B：裸机 jar
cd deploy && ./build.sh && cp .env.example .env
./scripts/start-all.sh    # 启动 5 个后端（日志 deploy/logs/、PID deploy/.pids/）
./scripts/stop-all.sh     # 停止
# 前端由宿主机 Nginx 托管构建产物（deploy/nginx.conf，监听 8080）
```

### 3.2 Nacos 控制台说明

| 项 | 值 |
|---|---|
| 控制台（开发本机） | http://127.0.0.1:8080（Nacos 3.x 控制台，认证关闭免登录）或 http://127.0.0.1:8848/nacos |
| 服务列表 | 「服务管理 → 服务列表」应见 5 个服务：gateway-service / auth-user-service / task-service / notification-service / stats-service，各至少 1 个健康实例 |
| 裸机生产 | 若对外暴露请开启鉴权（deploy/.env 的 NACOS_AUTH_*，见 .env.example 注释） |
| 配置管理 | 本期配置均内嵌各服务 application.yml，Nacos 仅作注册中心；配置中心预留未启用 |

常见检查：某服务重启后网关报 `No servers available for service: xxx` → 到控制台确认该服务实例已注册（注册需数秒~十几秒）；也可用 `curl http://127.0.0.1:8848/nacos/v1/ns/instance/list?serviceName=task-service` 查实例。

### 3.3 RabbitMQ 管理台说明

| 项 | 值 |
|---|---|
| 管理台 | http://127.0.0.1:15672（开发默认 guest/guest；生产改 RABBITMQ_USER/PASSWORD） |
| 用途 | task-service 事件 outbox → 通知/统计：交换机 + 队列承载 task 领域事件 |
| 排障入口 | 「Queues」看积压；对信封「Get message」可人工重投（M5 幂等验证即用管理台重投同一信封，消费幂等不脏数据） |
| 运维注意 | 生产换默认口令并新建业务 vhost；通知/统计服务消费失败重投机制由 outbox 生产者保证，队列可手动 requeue |

### 3.4 日志位置

| 环境 | 位置 |
|---|---|
| 开发（源码） | `TaskFlow/logs/{gateway,auth-user,task,notification,stats}-service.log`、`frontend.log`（Vite）、`access_log.*.log`；logback 按天滚动（`logs/${appName}.%d{yyyy-MM-dd}.log`） |
| 部署（裸机 jar） | `deploy/logs/*.log`（deploy/scripts/start-all.sh 的 LOG_DIR） |
| 部署（容器） | `docker compose logs -f <service>` |
| 中间件 | Nacos：`~/Downloads/nacos/logs/`（本机 standalone）；RabbitMQ：brew 日志目录；PostgreSQL：brew services 日志目录 |
| 关键日志关键词 | 权限回源自愈：task/stats 日志 `回源 auth-user-service`；登录锁定：auth 日志 `锁定`；邮件失败：notification 日志 `邮件发送失败` |

### 3.5 备份与恢复（RPO 24h / RTO ≤ 4h，详见 deploy/README.md §7）

- 每日备份：`cd deploy && ./scripts/backup.sh`（或 cron `15 2 * * * …`）。内容：4 个库 pg_dump 自定义格式（auth_user_db/task_db/notification_db/stats_db）+ 附件目录 + MANIFEST.txt；按 `BACKUP_KEEP_DAYS`（默认 7）滚动，满足 RPO 24h。
- 恢复示例（单库）：

```bash
pg_restore -h 127.0.0.1 -U postgres -d task_db --clean --if-exists \
  deploy/backups/2026-09-09_021500/task_db.dump
# 附件目录从同批次 backups 恢复；4 库 + 附件必须同一批次，避免事件/引用错位。
```

- 数据保留策略见 PRD 7.5：任务/时间线永久；审计 1 年（之后转冷存 3 年）；站内消息 180 天；邮件记录/导入批次 1 年（服务内置定时清理任务，notification-service 04:30、task-service 04:10）。

## 4. 常见故障排查表

| 症状 | 可能原因 | 处置 |
|---|---|---|
| 改了权限矩阵后个别接口仍 3001 | 权限缓存未及时回源 | 正常设计为"变更即时生效 + 主动失效 + 未命中回源自愈"（M5 实测清空缓存后首请求自动回源 auth-user-service 回填）。应急：`redis-cli del auth:perms:{roleKey}` 后该角色下一请求自动回源重建；姓名空白同理删 `auth:user:snapshot`（登录/lookup 触发重建） |
| 站内消息正常但收不到邮件，notification 日志 `邮件发送失败` | SMTP 未配置 / 本机无邮件服务器 | 设计行为：重试 3 次（1s/2s/4s 指数退避）→ mail_record 记 failed + 给全体系统管理员写站内告警 `mail.failed`，**不阻塞业务**。处置：配置 SMTP 环境变量（SMTP_HOST/PORT/USERNAME/PASSWORD/MAIL_FROM）后重启 notification-service；历史失败邮件不自动补发，可在 RabbitMQ 管理台对对应信封重投（消费幂等） |
| 删除待办任务返回 HTTP 500 / code 5000 | 已知缺陷：任务带评论/附件时物理删除触发 FK 冲突（见 [安全核查清单](安全核查清单.md) §5.3） | 应急：先 `DELETE /task/api/v1/comments/{commentId}`（附件同理）删净从属数据后重试；正式修复见遗留清单 |
| 登录提示"账号锁定中（3003）" | 连续错密 5 次，锁 15 分钟 | 等 TTL 到期（Redis `auth:lock:{account}` TTL=900s）自动解锁；值班应急可 `redis-cli del auth:lock:{account} auth:fail:{account}` |
| 改密后立刻重新登录被 3005 | JWT 无 jti：改密令牌已拉黑，同秒重登产出相同令牌（见 [安全核查清单](安全核查清单.md) §5.2） | 避免同秒重登（等 1~2 秒后再登录即新 iat）；正式修复见遗留清单 |
| 网关报 `No servers available for service: xxx` / 503 | 服务重启中/未注册 Nacos | 到 Nacos 控制台确认实例上线（数秒~十几秒）；仍异常看该服务日志是否启动失败（端口占用/DB 连不上） |
| 导入整批拒绝 code 2012 | 文件有错行（处理人账号不存在/停用、日期格式、进度非 5 的倍数等） | 响应的 details 给出逐行错误 [{row, reason}]；按提示修正重传，用 `GET /task/api/v1/tasks/import-template` 下载模板 |
| 导出 code 2010 | 筛选结果 >10000 行（PRD 上限） | 缩小筛选范围（状态/优先级/时间段/关键字）后重导 |
| 用户登录后 UI 一直弹强制改密 | must_change_password=TRUE（新建/重置后正常） | 按 1.2 完成改密即清除标记 |
| 前端 401 且"令牌无效" | 令牌过期（2h）/登出/改密后旧令牌进黑名单 | 前端应走 `POST /auth/api/v1/refresh`（刷新令牌 7 天）续期；否则重新登录 |

## 5. 上线前必办清单（汇自 6.4 安全核查）

1. **环境变量全覆盖**：`JWT_SECRET`（5 服务一致）、PostgreSQL/Redis/RabbitMQ 口令、SMTP、Nacos 鉴权（生产暴露时）——见 deploy/.env.example 与 [安全核查清单](安全核查清单.md) §4；
2. **补关键接口限流**（PRD 7.3.4，错误码 1003 已留）：网关 RedisRateLimiter（登录按 IP、写接口按账号）+ Nginx limit_req 兜底，未实现项须上线前落地；
3. **全站 HTTPS**：按 [安全核查清单](安全核查清单.md) §2.9 nginx 443 片段（内网可由网关终止 TLS）；
4. admin 首次登录完成强改密、生产口令随机化；API Key 仅绑定 taskAdmin 服务账号并留痕；
5. 部署产物使用 deploy/（M6.3）双路径任一完成干净环境演练后再上线。
